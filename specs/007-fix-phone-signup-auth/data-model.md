# Phase 1 Data Model: Phone Sign-Up Authentication Fix

## Schema Changes

**None.** No migration is required (constitution VI satisfied without one).

The `VerificationToken` model already carries every field this feature needs:

```prisma
model VerificationToken {
  identifier String
  token      String
  expires    DateTime

  @@id([identifier, token])
}
```

The `expires` column is already written by `requestPhoneOtp`. It was simply never read. This feature makes it authoritative — the field exists, so the fix is a read, not a migration.

---

## Entity: One-Time Code Record

The `VerificationToken` row is reused for three unrelated purposes, distinguished by the `identifier` prefix. **Purpose scoping is a correctness requirement** (FR-012): a code issued for one purpose must never satisfy a check for another.

| Identifier form | Purpose | Issued by | Verified by |
|---|---|---|---|
| `otp:{+989XXXXXXXXX}` | Phone sign-in / sign-up verification | `requestPhoneOtp` | `checkSmsOtp` / `consumeSmsOtp` |
| `pwreset:{email}` | Password reset link | `requestPasswordReset` | `resetPassword` (reads `expires` already) |

### Fields

| Field | Type | Rules |
|---|---|---|
| `identifier` | `String` | `otp:{e164Phone}` or `pwreset:{lowercasedEmail}`. Part of the composite primary key. |
| `token` | `String` | SHA-256 hex digest of the code. **The plaintext code is never stored.** Part of the composite primary key. |
| `expires` | `DateTime` | Moment after which the code is rejected. For OTP: **now + 2 minutes**, computed at the instant the SMS is sent. |

### Validation Rules

- A code is **valid** iff a row exists for `(otp:{phone}, sha256(code))` **and** `row.expires > now`.
- `identifier` MUST match the phone the code was issued to. A code issued to number A MUST NOT verify number B, regardless of the code value (FR-018, FR-019).
- Codes are compared by hash, never by plaintext equality.
- Length: 6 digits for codes generated by `generateOtpCode`. The dev master codes are 6 digits (`123456`).

### Uniqueness / Collision Behaviour

The composite primary key `[identifier, token]` means two codes for the same phone differ by `token` and can coexist. `requestPhoneOtp` already calls `deleteMany({ where: { identifier } })` before creating, so **only the most recent code for a number survives** (FR-007, FR-021). This is deliberate: an older outstanding code must become unusable the instant a newer one is issued.

## OTP Lifecycle

```text
                  requestPhoneOtp
                        │
                        ▼
                 ┌──────────────┐
                 │   ISSUED     │  row written, expires = now + 2min
                 └──────┬───────┘
                        │
        ┌───────────────┼───────────────┐
        │               │               │
   check (non-      consume           2 min elapse
   consuming)       (single-use)          │
        │               │               ▼
        ▼               ▼          ┌──────────┐
   still valid      still valid   │ EXPIRED  │
   (account may     (session made)└──────────┘
    be created)          │
                         ▼
                  ┌────────────┐
                  │ CONSUMED   │  row deleted; code can never be used again
                  └────────────┘
```

### State Transitions

| From | Event | To | Effect |
|---|---|---|---|
| — | `requestPhoneOtp` | ISSUED | Prior rows for the same identifier deleted; new row written with `expires = now + 2min`; SMS sent |
| ISSUED | `checkSmsOtp` with correct, unexpired code | ISSUED | **No change.** Verification passes without consuming — this is what unblocks account creation |
| ISSUED | `consumeSmsOtp` with correct, unexpired code | CONSUMED | Row deleted. Session is established from this proven credential |
| ISSUED | `checkSmsOtp` / `consumeSmsOtp` with wrong code | ISSUED | No change. Caller reports "incorrect code" |
| ISSUED | `consumeSmsOtp` after `expires` passes | ISSUED | Rejected. Caller reports "expired" — distinct from "incorrect" (FR-006) |
| CONSUMED | any verification attempt | — | Rejected. No row exists; single-use is guaranteed structurally |
| ISSUED | Phone field released, number changed | — | Pending code for the previous number is discarded so it can never be submitted against a new number (FR-019) |

### Invariant (the core of this feature)

> A code is verified at most once to authorize an action, and consumed at most once in total, during a single sign-up attempt.

The pre-fix flow violated this: `consumeSmsOtp` ran once before account creation and again inside the SMS provider's `authorize()`, so the second call always failed against an already-deleted row.

## Entity: Shopper Account

Unchanged. The `User` model is untouched by this feature.

Relevant existing constraints:

- `mobile` is unique — enforces one account per number.
- `email` is unique and nullable.
- `banned` blocks session creation regardless of verification outcome (handled in the Auth.js `jwt` callback, which throws for banned users).

### Account Creation Ordering

```text
1. rate limit check
2. duplicate check (email OR mobile)
3. checkSmsOtp  ── fails → "invalid code" / "expired"; NO account created
4. create account
5. record notification
6. establish session (consumes the code)
7. redirect /user/profile
        │
        └─ session fails → account KEPT (never deleted) → toast → /sign-in
```

Steps 3 and 6 both touch the code, which is why the check/consume split (R1) is required. Step 4 precedes step 6 necessarily: there is no account to sign in until it exists.

**Ordering constraint**: verification must gate creation (R2). Creating first and verifying second would leave an unverified account occupying the mobile number, and the shopper's retry would be rejected as "account exists" — a permanent dead end.

---

## Identity & Uniqueness Rules

- A phone number identifies at most one account (`mobile` unique).
- An email address identifies at most one account (`email` unique).
- Either may be null, but never both — a phone sign-up with no email is valid; a sign-up with neither is rejected by the schema.
- Google OAuth uses `allowDangerousEmailAccountLinking`, so a Google sign-in for an existing email links to the existing account rather than creating a duplicate. This is unchanged by this feature.

---

## Data Volume Assumptions

- VerificationToken rows are tiny — at most one live OTP row per phone number, plus password-reset rows.
- Sign-up is a low-volume operation on this store. No pagination, no archival, no partitioning required.
- Expired rows are not swept. They are rejected at read time and overwritten on the next request for the same number. Acceptable at this scale (R4).
